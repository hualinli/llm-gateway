## 3. 被测面与组织/资金播种

* 每轮都走**计费路径**：`auth → access guard(pg) → billing admission(pg，预占) → limiter(Redis) → 活跃流上限 → 上游`。没有为了跑分关闭任何正式 profile 的资金/权限开关（`GATEWAY_BILLING=pg`、`GATEWAY_ACCESS_GUARD=pg` 全程开启）。
* 每次运行由 `scripts/capacity-report.py` 自己播种：1 个 `t11-capacity@t11.test` 用户、**1 个热组织 + 10 个多钱包组织**（共 11 个 org / 11 把 Key）、每个组织 `posted_balance_micro=10^12` 与一条对应 `credit` 流水、价目 `model=default` 输入/输出 `1000000 micro/百万 token`（= 1 micro/token），`effective_at=2026-01-01`（固定值，便于复跑幂等）。
* 直连轮（`b01-direct-*`）打 `mock-primary` 直连端口，**不产生任何平台账**，因此不进入 §8 的对账期望值。

## 4. 方法、计划与对验收规格的偏离

### 4.1 交付的 runner

`scripts/capacity-report.py`（新增，纯标准库）承担 T11 的隔离容量实验：

* 独立 Compose project/端口/卷/run_id；`ports: !override`；镜像按 commit 固定 tag（`llm-gw-cap-<commit8>-<service>`）以便 `--no-build` 精确复用；
* 每轮报告 scheduled/started/completed/rejected/transport_error/incomplete/cancelled/parse_error/loadgen_dropped/peak_active、计划 vs 实际启动速率、到达率、dispatch_lag、scheduled_to_terminal、first_event/first_content/stream_duration（p50/p95/p99/min/max/avg）；
* **有效性规则内建**：任一生成器丢弃 >0.1% 或（开环轮）到达率 <99% 计划 → 该轮 `capacity_round_valid=false`，报告中单列且不用于容量结论（`cmd/loadtest` 自身也发布同一规则，runner 再按轮聚合复算一次）；
* 多生成器（1v2 需要按实例分摊、慢客户端需要按比例混合、多钱包需要每组织一个 Key）：合并口径 = 求和，百分位**逐生成器报告**并在表头标注"未合并百分位"；
* 采样：Gateway/Metering/Console `/metrics`（1–2s）、`docker stats`（3s，全部本项目容器）、PG（2s：后端连接/等待锁/行锁/等待事件/事务数/未结算收据/结算积压）、Redis（2s：ops/客户端/内存 + 宿主侧 PING RTT）；每轮结束抓一份完整 `/metrics` 原文（`resources` 中的 `full_metrics_snapshots`，含直方图分位数）；
* 指定轮次抓 pprof（CPU/heap/goroutine/mutex/block）并用本地交叉编译的 Linux gateway 二进制符号化；
* 收尾做 run-scoped 对账（§8）、写 `manifest.json`（路径+字节+sha256，>400 KiB 的文件只登记不入库）。

用法（完整复现见 §10）：

```text

  [--experiments all|smoke|up|b01|closed-ladder|open-ladder-s|open-ladder-l|gw1v2|wallets|slowclient|overload] \
  [--step-seconds 60] [--warmup-seconds 30] [--rounds 3] [--slow-stop-seconds 30] \
  [--overload-seconds 180] [--fallback-seconds 180] [--no-build] [--keep] [--allow-dirty] \
  [--reuse-rounds] [--republish] [--dry-run]
```

## 5. 实验结果

### 5.1 B01：直连 vs 完整 Gateway（低负载，S/M/L）

| 形状 | 侧 | 轮数 | first_content p50 (ms) | first_content p95 (ms) | 计划/到达/启动 (req/s) | 完成 | scheduled_to_terminal p95 (ms) | Gateway CPU 秒/轮 | Gateway RSS 峰值 (MiB) |
|---|---|---|---|---|---|---|---|---|---|
| S | direct | 3 | 21.84 | 23.73 | 25.02 | 4500 | 139.66 | 0.2 | 31.77 |
| S | gateway | 3 | 25.7 | 28.81 | 25.02 | 4500 | 145.54 | 6.1 | 29.85 |
| S | **增量 (gateway-direct)** | – | **+3.86** | **+5.08** | 0 | 0 | 5.9 | +5.9 | -1.92 |
| M | direct | 2 | 101.78 | 106.12 | 4.02 | 480 | 2286.39 | 0.18 | 31.66 |
| M | gateway | 2 | 106.15 | 110.15 | 4.02 | 480 | 2236.02 | 3.29 | 30.77 |
| M | **增量 (gateway-direct)** | – | **+4.37** | **+4.03** | 0 | 0 | -50.4 | +3.11 | -0.89 |
| L | direct | 1 | 302.46 | 307.36 | 2.02 | 120 | 11345.42 | 0.25 | 29.63 |
| L | gateway | 1 | 306.36 | 310.44 | 2.02 | 120 | 11244.0 | 5.24 | 32.82 |
| L | **增量 (gateway-direct)** | – | **+3.9** | **+3.08** | 0 | 0 | -101.4 | +4.99 | 3.19 |

* 每形状的 3 轮/2 轮离散极小（S：direct p50 21.6–21.9ms、gateway 25.6–25.9ms），差值稳定可复现。
* `scheduled_to_terminal` p95 在 M/L 上主要由流本身时长决定（M≈2.2s、L≈11.2s），网关侧差异在噪声内（M −50ms、L −101ms，即 gateway 反而略快，属于抖动）。
* Gateway CPU：S 25/s 时 6.1 CPU 秒/1500 请求 = **4.1 ms/请求**；M 4/s 时 3.3 秒/240 请求 = 13.7ms/请求（长流 + 每流终结/收据）；空闲基线 0.18–0.25 秒/轮。

## 7. 第一个瓶颈：PostgreSQL 写路径（准入 + 结算共用）

### 7.1 结论

**本次运行里第一个（也是最主要的）瓶颈是 PostgreSQL 上计费写路径的共享容量，而不是 Gateway 的 CPU、Redis 或活跃流上限。**

* 现象：S 形状接纳速率在 **≈198–200/s** 封顶（200/s 与 300/s 两档分别接纳 198.3 / 199.7/s，500/s 档 173.3/s）；
* 同期 Gateway 只用 **0.85 核 / 4 核**（52.3 CPU 秒/61.5s），CPU profile 显示时间在 syscall I/O；
* 同期 PG CPU 峰值从 194%（100/s）涨到 **539%**（300/s），事务率封顶 ~1.8k/s，且出现 `IO:WalSync`/`LWLock:WALWrite`/`Lock:transactionid` 等待；
* 每请求的 PG 工作量是"多条事务"级别：一次被接纳的请求 = 预占（`billing_entries` reservation + `billing_accounts` 行锁更新）+ 执行状态推进 + 收据插入；结算再叠加 debit + release + 账户更新 + 收据状态更新。本次运行总账本行数 552974 行 / 186591 次启动 ≈ **2.96 行/请求**，加上执行/收据状态更新，300/s 档实测 1807 事务/s ≈ **9 事务/接纳请求**。
* **拒绝也不免费**：503（活跃流上限）发生在计费准入**之后**（`cmd/gateway/main.go` 的中间件顺序：auth → guard → billing admission → limiter → stream limit → proxy），因此每个 503 仍然产生一次预占+一次释放（本轮 6806 个非完成启动 = 6806 条 `failed_no_charge` 执行 + 6806 条 reservation + 6806 条 release）。过载时 17% 的流量是"付了 PG 写代价但被拒"的请求。

### 7.2 不能据此断言的

* 不能断言"PG CPU 100% 饱和"：VM 有 20 核，PG 峰值 5.4 核；真正的限制更可能是 **WAL fsync/写序列化（`IO:WalSync`、`LWLock:WALWrite`）** 与同一账户行的 `FOR UPDATE` 串行化叠加，而不是核数用尽。本次没有采集 `pg_stat_statements`/单语句耗时，也没有单独压 PG（**未验证**，§11）。
* 热钱包 vs 多钱包的对比（§5.5）证明账户行锁是**可测量的尾部贡献者**（p95 −27%、行锁 2–3 → 0–1），但在这个并发水平上它还没有成为吞吐瓶颈。

## 11. 本机限定与未验证清单

**环境限定**

1. 单台 Intel macOS（x86_64）+ OrbStack VM：Gateway/PG/Redis/Mock/发压器同机共享 CPU 与磁盘，绝对吞吐、PG I/O 延迟都不能外推生产；正式容量结论需要稳定 Linux、发压机分离（§3.2）。
2. 运行期间同宿主还有其它实验的容器（`llm-gw-t11-ab-*`、`t01a-*`、`tokmall-*`、`t11-pgbench-probe`），本 runner 不控制它们的负载；已把开始/结束时的 CPU/内存快照记入 `environment.json.foreign_containers`。
3. PG/Redis 无 CPU/内存限制、Gateway 有 cgroup 上限（4 或 8 核）："PG 是瓶颈"的判断包含"PG 不受限而 Gateway 受限"这一非对称，生产部署需要重新确认。

**未测量/未验证**

1. **60 min soak 未做**：无法回答长时间稳态下 RSS/积压/结算是否漂移。
2. **durable finalization P99 未测**：Gateway 没有"usage 完整 → receipt 持久化"的直方图；只有结算延迟（receipt 落库后），§6.2 的 ≤100ms 门槛本次无法判定。
3. **结算 SLO 只在低负载成立**：≤100 收据/s 时最老未结算 <1s；≥200/s 时 38–146s，明显超过 §6.2 的 P99 ≤5s 候选门槛。这是"共享 PG 写路径"的直接后果，但**未**单独压测结算管线（未跑 `METERING_SETTLEMENT_*` 调参 A/B）。
4. **S 形状的拒绝模式未测**：200/s 以上生成器的有界准入队列先于 Gateway 拒绝，观测到的都是生成器丢弃；要测 S 的 429/503 需要更深队列或第二台发压机（B00 的教训在本形状上重现）。
5. **1v2 的"翻倍资源"档未做**：只做了"总资源匹配"（1×8CPU/512 流 vs 2×4CPU/2×256 流），没有做 1×4CPU/256 流 vs 2×4CPU/2×256 流（翻倍资源）对照。
6. **大事件形状（1KiB/64KiB/1MiB/超限）未做**；`cmd/loadtest` 已支持，本次未纳入容量矩阵。
7. **1000 钱包 / 100–10000 Key / 1000 用户未做**：只测了 1 与 10 钱包、11 把 Key。
8. **管理 API（Console）容量与 ab 未做**：Console 只作为被采样容器（整轮 RSS 峰值 14.2 MiB、CPU 峰值 3.9%；Metering 47.0 MiB/264.5%、Mock-primary 30.2 MiB/82.9%、PostgreSQL 256.4 MiB/559.3%），未做 §4.2 的分页/聚合读压测，也未做"管理查询与 M/L 流并发"的隔离实验。
9. **依赖故障恢复（B07/F01–F20）不在本报告范围**：本报告只覆盖过载回落恢复；故障矩阵见 `docs/verification/2026-10-01/t10-failures/`。`t11-recovery-report/` 由另一 agent 负责。
10. **mutex/block pprof 拿不到**：进程未开启 mutex/block profiling（仓库无 `runtime.SetMutexProfileFraction`/`SetBlockProfileRate`），需要改 Go 代码；本报告用 PG 锁等待与 Redis 延迟替代。
11. **慢客户端占满槽位后快客户端的拒绝临界点未单测**：本曲线只到 50% 混合（快流未受影响）。
12. **未做跨配置 A/B 轮换（AB/BA）**：同配置内做了重复轮，跨配置只做了顺序对照。
13. **优化项（B10）未做**：没有对已定位瓶颈做单项优化与前后对照；§7 只给证据与候选机制（WAL 写序列化、账户行锁、结算与准入竞争 PG）。
14. **逐请求日志证据只覆盖一轮**：`compose-logs.txt` 用 `--tail 3000` 抓取，被 Gateway 的逐请求 `billing admission` 日志与 Metering 的逐收据结算日志淹没，只留下最后一个 Gateway 实例的第一分钟（`gw1v2-perorg-gw2`）；其余轮次的准入延迟只能通过 `/metrics` 直方图与客户端延迟间接观察。
15. **1v2 的 two-gateway 轮按实例分摊生成器**（`split_across_targets`），因此每实例的 `-c/-n` 是总量的一半；合并口径是求和，百分位**逐生成器**报告，未做百分位合并。

## 12. 文件清单与 manifest

* `raw/<round>.json`（54 个）：每轮的合并记录 —— 生成器完整 accounting/rates/latency/status、`load_profile`（含 c/n/rate/shape/queue/timeout）、聚合口径与有效性判定、资源摘要、pprof 索引。
* `resources/<round>.json`（54 个）：每轮资源摘要（Gateway RSS/heap/goroutine/FD/CPU 峰值与首末差、各容器 CPU/内存峰值、PG 锁/连接/事务/积压、Redis ops/RTT）+ 指向完整采样序列的路径。
* `profiles/`：pprof 文本（CPU/heap top、goroutine 摘要、mutex/block 空样本证据）。
* `index.json` / `summary.json` / `report-tables.md`：全部轮次与按实验中位数/范围（README 表格的来源）。
* `reconciliation.json`：§8 的全部断言与 PG 事实。
* `environment.json` / `parameters.json` / `plan.json` / `timeline.json`：环境、参数、计划、阶段时间线。
* `manifest.json`：全部 542 个文件的路径/字节/sha256 与 `committed` 标记；完整采样序列、`loadtest`/`gateway` 二进制（10.3 MB / 38.3 MB）与 compose 日志留在 gitignored 的 `data/benchmarks/t11-capacity/`，只登记不入库。
* 本次运行没有留下任何容器或卷（`docker ps -a`/`docker volume ls` 按 `llm-gw-cap` 过滤为空）。
