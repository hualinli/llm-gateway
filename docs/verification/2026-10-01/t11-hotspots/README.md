## 2. B03 热点 A/B

### 2.1 两个实现与「只有一条生产路径」

| | A（shipped，`internal/billing/{execution,account,settlement_settle}_pg.go` 的形状） | B（实验，仅存在于 harness） |
|---|---|---|
| admission | `EnsureAccount` → **`SELECT … FOR UPDATE`（在价格/重放读之前拿锁）** → 价格版本 → 重放检查 → 插 execution → 插 reservation 流水 → `UPDATE billing_accounts SET posted=?, reserved=?`（绝对值）→ 审计 | `EnsureAccount` → 价格版本 → 重放检查 → **`UPDATE … SET reserved_micro = reserved_micro + $2 … WHERE org_id=$1 AND status='active' AND posted_balance_micro - reserved_micro >= $2 RETURNING`** → 插 execution → 插流水 → 审计 |
| settlement | receipt 锁 → execution 锁+守卫更新 → 每个 posting：(ensure → 账户 `SELECT … FOR UPDATE` → 重放检查 → 插流水 → 绝对值 UPDATE → 调整审计) → receipt 置 settled → 结算审计 | 同样的 receipt/execution 锁、同样的流水与审计，只把每个 posting 的账户写换成条件/相对 UPDATE（release 带 `reserved_micro >= $2`） |
| 语句数 / 临界区 | 8 条 / 锁后的 7 条 | 7 条 / 锁后的 4-5 条 |

`sqlcheck` 把 shipped SQL 的每一段（列清单、WHERE、`FOR UPDATE`、`RETURNING`）当锚点
（31 个），Go 源码一改就拒绝运行 —— 避免「测的形状已经不是产品形状」。B 侧语句不在 Go 源码里，
这是刻意的：**生产仍然只有一条资金路径**，harness 只是把两种事务形状放到同一台 PG 上对照。

### 2.2 资金等价性门禁（先过门禁，再比性能）

`hotspot` 每次运行先跑这个门禁（两个变体各一次）：钱包恰好够 25 份预占（25×89 micro），
100 个线程用 `threading.Barrier` 同时发起：

| 变体 | 资金结果（4 次独立运行完全一致） | 无透支 | 投影=账本 | 流水=execution | version | 审计 | 放行 p50（4 次，ms） | 拒绝 p50（4 次，ms） |
|---|---|---|---|---|---|---|---|---|
| A `for_update` | 25 成功 / 75 `insufficient_funds` | ✅ | ✅ | ✅ 25/25 | 26 ✅ | 25 | 89.3 / 83.5 / 237.9 / 92.2 | 215.0 / 185.5 / 454.6 / 205.9 |
| B `cond_update` | 25 成功 / 75 `insufficient_funds` | ✅ | ✅ | ✅ 25/25 | 26 ✅ | 25 | 103.2 / 85.8 / 222.7 / 100.7 | 182.0 / 157.6 / 480.8 / 176.7 |

（4 次运行 = `hotspot-summary-{reserve,ensure,settle,driver}.json`，每次 `hotspot` 调用都会先跑这个门禁。）

两者都满足：`reserved_micro == 25×89`、`posted == 25×89`（账户只被这 25 笔预占影响）、
没有第 26 笔预占、没有负 reserved、没有重复流水、`version == 26`。
**拒绝路径 B 在 4 次里 3 次更快（−15% / −15% / −8%，1 次 +6%）**：它不需要在拒绝前先持锁，
而 A 在 `SELECT … FOR UPDATE` 之后才发现余额不够、rollback 时仍然握着锁。放行路径两者互有胜负。

### 2.3 测量方法

- 客户端：`pgbench -M prepared` 在容器内跑（C 客户端，避免 Python 逐语句开销掩盖锁等待）。
- A/B **同进程、按事务 1:1 交替**（`-f A@1 -f B@1`）：客户端数、连接、缓存、时间窗完全一致，
  比跨轮 ABBA 更强；每 cell 3-4s，另有 `driver` 控制 cell（`SELECT 1` + 事务）给出生成器上限。
- 延迟：pgbench `-l` 全量事务日志的精确分位数（微秒级），不是平均值近似。
- 「锁平均」：pgbench `-r` 里**真正拿锁的那条语句**的平均延迟（A= `SELECT … FOR UPDATE`，
  B= 条件 `UPDATE`）。settle 场景里同一段 SQL 在事务内出现两次（debit/release），
  因此这个数字是两个账户写的平均，已在 harness 注释里写明。
- PG 侧：每 0.1s 采样 `pg_stat_activity`（Lock/LWLock 等待者、active）与容器 cgroup `cpu.stat`。

### 2.5 瓶颈归属：行锁、CPU、还是客户端

Lock 等待者极值（`pg_stat_activity`，每 0.1s 采样，3s 窗口）与容器 CPU：

| concurrency | 1 钱包 | 10 钱包 | 1000 钱包 |
|---|---|---|---|
| c=8 | 0 (7.1 CPU·s) | 0 (6.5) | 0 (7.0) |
| c=16 | **2** (11.7) | 0 (12.1) | 0 (11.7) |
| c=32 | **14** (10.0) | 3 (11.0) | 0 (10.5) |
| c=64 | **18** (18.6) | 0 (17.9) | 0 (17.2) |
| c=128 | **77** (12.3) | 17 (12.7) | 0 (12.5) |

（括号内是该 3 秒 round 内容器消耗的 CPU 秒数，20 核容器。）

- **行锁确实存在**：只有共享钱包时才有 Lock 等待者，且随「每钱包客户端数」增长；
  1000 钱包（每客户端独立钱包）一个都没有。锁语句平均延迟从 0.16ms(c=1) 涨到 12.5ms(c=128)。
- **但吞吐上限不是行锁**：1 钱包与 1000 钱包在同一并发下吞吐相同（c=64: 1787 vs 1679 tx/s；
  c=128: 1405 vs 1432 tx/s），而容器在 8 个客户端时就烧掉 2-7 个核、c=64 时烧掉 ~6 个核。
  即：**这台机器上第一个瓶颈是每语句 CPU（Docker Desktop VM 的 CPU 预算 + 并行容量任务占用的宿主），
  行锁只表现为排队延迟**。在没有稳定 Linux 机器的前提下，不能把「1 热钱包不是瓶颈」推到生产环境；
  能确定的只是：在本环境里把锁换成条件更新**不能**提高吞吐。
- 客户端不是瓶颈：`driver` 控制 cell 的 2 往返事务在 c=128 时仍有 ~38k tps，而 reserve 事务
  ~1.4-1.9k tps，差 20 倍。

### 2.6 噪声带：同一份脚本，两次独立运行

把「`--ops ensure` 的 with_ensure 脚本」与「`--ops reserve` 的 for_update 脚本」相比：
**两者是逐字节相同的脚本**（同样的语句、同样的 org 表达式），只是在不同 run、不同容器里跑。
24 个配对 cell 的差异就是这台机器的跨轮噪声：

| 指标 | 中位数 | 范围 |
|---|---|---|
| 吞吐 | -10.7% | -68.9% … +74.8% |
| p50 | -5.4% | -47.9% … +166.9% |
| p99 | +10.4% | -57.7% … +163.5% |

（本 run 期间并行的容量任务 `llm-gw-cap-*` 在跑阶梯；宿主 20 核、`vm.loadavg` ~8。）

**结论**：A/B 的差异**小于同一脚本的跨 run 噪声**（下表是同一份脚本两次运行的差异，包含宿主漂移）：

| 指标 | 同 run 内 B−A（36 个 cell） | 同一脚本跨 run（24 个配对） |
|---|---|---|
| 吞吐 | 中位 -0.7%（-9.5% … +4.8%） | 中位 -10.7%（-68.9% … +74.8%） |
| p99 | 中位 +9.5%（-7.7% … +99.8%），34 / 36 个 cell B 更差 | 中位 +10.4%（-57.7% … +163.5%） |

同 run 内交替比较仍然有效（两者共享同一时间窗），它给出的稳定结论只有三条：
1. 吞吐持平（B−A 中位 -0.7%，两个方向都有）；
2. B 的 p99 在中位意义上更差（+9.5%，且 34 / 36 个 cell 同向），锁语句平均延迟也一致更高；
3. 拒绝路径 B 在 4 次门禁里 3 次更快（§2.2）。

### 3.4 日汇总值不值得做

**不直接上线，但把它的语义成本量化清楚。**

- 汇总表本身是**正确**的：整段历史与「整日窗口」两侧完全相等（`whole_history.equal=true`、
  `whole_day_window.equal=true`，100k 与 1M 两个 tier 都是）；构建成本很低
  （100k: 0.07-0.10s，1M: 0.31-0.33s，见 `raw/query-*.json` 的 `rounds[].schema.rollup_build_seconds`）。
- 但本 API 的窗口是任意 `[from, to]`（`internal/console/usage_pg.go` 的 `created_at >= $2 AND created_at <= $3`），
  而日汇总只能回答**整天**。用「包含该窗口的整天」去回答，多算的就是「落在窗口外、但在边界整天内」的行：
  本次 1M tier 多算 **1,405 行（+0.70%）**、100k tier 多算 **9,267 行（+46.3%）**。
  两个数字的差别来自测量本身：100k tier 的那 9,267 行主要是 harness 自己的写脚本在测量期间插入的新事件
  （`created_at = now()`，落在请求窗口之外、却在「今天」这一天之内）——**这正是日汇总会引入的错误类别**：
  任何「窗口外、边界整天内」的流量都会被计入。
- 短窗口更糟：一个 1 小时的窗口在日汇总下会被放大成 24 小时；本次 31 天窗口的误差只有边界两天，
  所以看起来「只有 0.70%」，这是窗口长度与边界流量的函数，不是精度保证。
- 因此**结论：先做索引（零语义变化、−85% 模型过滤页 / −77% 合计）；日汇总只有在明确接受
  「按整天报告」或补一条「边界天走明细」的残差查询之后才值得做**。若要做，建议按小时汇总
  （把误差压到 ≤1/24 天），而不是按天。

## 4. 已知限制

1. **单台 macOS + Docker Desktop Linux VM**（容器可见 20 vCPU，但宿主同期在跑并行容量阶梯，
   `vm.loadavg` ~8）：§2.6 量到的同脚本跨 run 噪声是吞吐 −69%…+75%、p50 −48%…+167%，
   所以本报告的**绝对吞吐/延迟只能当量级**，不能当容量结论；A/B 结论依赖同 run 内交替比较。
2. **没有稳定 Linux 机器**，因此「这台机器上第一个瓶颈是每语句 CPU 而不是行锁」的归属不能外推到生产；
   能外推的只有「把 `SELECT FOR UPDATE` 换成条件更新，在两者都不缺 CPU 时不会更快」这一条。
3. `query` 的 100k/1M 数据集是**合成**的（50 组织、5 模型、均匀铺开、热组织占 20%），
   不是生产分布；索引收益对基数与选择性敏感。
4. 日汇总的维护成本没有测：本报告的 rollup 是一次性构建（1M 行 ~4-5s，数字在 `raw/query-1m.json`
   的 `rounds[].schema.rollup_build_seconds`），**没有实现同步触发器/夜间任务**，也没有测它对写路径的影响。
5. `pgbench -M prepared` 与 Go 的 pgx 在参数化/解析细节上不完全一致（前者客户端固定 prepared 语句），
   两者每事务往返次数相同；绝对数字因此系统性略有差异，A/B 不受影响。
6. settle 场景的「锁平均」列在事务内出现两次同类语句时是两者平均（已在 §2.3 写明），
   不能读成「第一次拿锁的等待」。
7. 每个 cell 只有 3-4s（不是 BENCHMARK §3.2 的 300s×3 轮），且故障/热点实验各只跑 1-2 次；
   本报告按「形状证据」而不是「稳定分位数」使用这些数字。
