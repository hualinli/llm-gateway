# 架构

读完[仓库说明](../README.md)后再看本文。本文按一次真实调用把代码指出来，并说明数据归谁写。产品规则见[业务方案](BUSINESS.md)，哪些已经验收见[当前状态](PROJECT-STATUS.md)。接口字段以[OpenAPI](openapi/console-v1.yaml)为准。

## 进程

浏览器只访问 Web。Nginx 把 `/api/v1` 转到 Console，把 `/v1` 转到 Gateway，这样会话、CSRF 和流式输出都在同一个源上。

| 进程 | 代码入口 | 职责 |
|---|---|---|
| Web | `web/` | 登录、切换账户、各角色的工作台。页面上没有的按钮不构成授权 |
| Console | `cmd/console` | 注册、会话、企业与成员、Key、模型目录、价格、账务查询。写入 PostgreSQL，配置经 Control 发布 |
| Control | `cmd/control` | Key 哈希、上游凭据引用、版本化路由。它是配置的唯一写入者。凭据明文不进普通配置快照 |
| Gateway | `cmd/gateway` | 认 Key、核对账户、限流、预占、转发 |
| Metering | `cmd/metering` | 派发用量收据、按实际 Token 结算、恢复卡住的预占 |
| PostgreSQL | — | 用户、组织、成员、价格、额度、执行、收据、流水、审计。各业务表有明确的写入进程 |
| Redis | — | 限流令牌和计量事件。不是账本 |

本地预览的默认地址：Web `127.0.0.1:5173`，Gateway `18090`，Console `18092`，Metering `18091`。

## 一次聊天请求

`cmd/gateway/chain.go` 的 `chatChain` 把中间件套成固定顺序。请求从外往里走：

```text
auth → gatewayguard → limiter → 组织并发上限 → billing → proxy
```

不花钱就能拒绝的请求停在预占之前：401、403、404、限流 429、组织并发 429。它们不写执行记录，也不冻结资金。

### 1. 认 Key：`internal/auth`

Gateway 内存里是一张哈希表，键是 API Key 的 SHA-256，值是 `KeyRecord`（`internal/auth/records.go`）。记录里没有明文，有编号、租户、组织、成员、过期时间和 Key 自己的模型范围。Control 每推一版配置，整张表替换一次。

`Authorization` 必须是 `Bearer` 加一个值。对不上快照就是 401。通过后，context 里同时放着租户字符串和整条 `KeyRecord`。生产路径上两者来自同一条记录。限流和日志读字符串；guard 读整条记录。

这一步不查数据库。快照可能落后于「成员刚被停用」这种事实。

### 2. 核对身份：`internal/gatewayguard`

`middleware.go` 从 context 取出 `KeyRecord`，调用 `Guard.Check`。接口有两个实现，启动时由 `cmd/gateway/accessguard.go` 按 `GATEWAY_ACCESS_GUARD` 选择：

| 值 | 实现 | 行为 |
|---|---|---|
| `pg` | `pg.go` 的 `PGGuard` | 预览和生产用这个。用 Key 哈希做一次只读查询 |
| `off` | `gatewayguard.go` 的 `SnapshotGuard` | 只看快照里的状态、过期和模型范围。不核对组织、用户、成员是否仍然有效。单测和早期代理调试用它 |

`PGGuard.Check` 先挡掉快照里已经过期或非 `active` 的 Key，以及没有组织编号的旧 Key。然后 `readFacts` 在一个只读事务里查 `api_keys`，连上组织、用户和**创建 Key 时记下的那一次成员关系**。人被移出后再加入会得到新的成员编号，旧 Key 对不上。查库失败是 503，不会因此放行。

`evaluate` 不再访问数据库。Key 不存在、状态不对、已过期是 401。组织、用户或成员无效，或者角色不是 `owner`、`admin`、`member`，是 403。客户端只看到笼统的 message；具体原因在日志的 `Reason` 里。

通过之后，中间件把查库得到的组织、用户、成员编号，加上新生成的 `exec_...`，放进 `Attribution`。后面的限流和预占用这份结果，不再用 auth 放进去的快照。

模型范围是四层交集，类型是 `*[]string`：`nil` 表示沿用上一级，指向空切片表示这一级拒绝全部模型，指向有元素的切片表示只能用列出的模型。任一层给了明确列表，中间件才去读请求体里的 `model`。未知模型 404，已知但不被允许 403。成员这一层的字段已经留在交集里，数据库还没有成员级列表，所以目前始终沿用上一级。账户内成员第一版共用账户可用模型。

非流式和坏 JSON 不在这里拒绝，留给代理回 400。

### 3. 限流：`internal/limiter`

按组织在 Redis 里扣令牌。没有发布组织策略时退回租户桶。本进程上该组织同时进行的流另有一个上限，满了也是 429。组织流上限和代理内部的全局流上限都是单实例的：两个 Gateway 进程时，并发流上限大约是配置值的两倍。跨进程共享的只有 Redis 里的令牌桶。

### 4. 预占：`cmd/gateway/billing.go`

只处理聊天和 Responses 的 POST。它按完整请求字节数（包含 JSON Schema）加模板开销估计输入上限，并固定输出上限，查出**此刻生效**的价格版本，再在一个 PostgreSQL 事务里检查余额和成员月额度并冻结这笔上限。价格版本写在执行记录上，之后改价不改变这一笔。

Chat 的计费入口只接受已列明的纯文本请求字段；工具、多模态、状态引用及未知扩展被拒绝。`GATEWAY_BILLING_MAX_INPUT_BYTES` 限制完整请求（含平台补入字段），默认 256 KiB；单条消息仍默认限制 64 KiB。估算要求上游遵守输出上限，且其 tokenizer 和模板开销符合配置；异常超额用量按真实值记录，不能宣称对任意兼容上游都不会低估。

成员额度为 `null` 表示不限额，`0` 表示禁止新消费。额度按准入时的北京时间自然月记账，迟到结算仍算进那个月。下调上限不会取消已经准入的请求。

全局活跃流上限在代理内部、预占之后。这种 503 会留下执行记录和一笔随后释放的预占。见[技术决策](decisions.md)里的 C5。

### 5. 转发：`internal/proxy`

按该模型、该协议已发布的上游列表依次尝试。5xx 或连不上，且还没向客户端写出字节，可以换下一家。已经写出内容就不能重放，否则客户端会看到两段答案。参数错误这类终态失败也不换上游。

流正常结束时，用量收据必须先落库，`[DONE]` 才发给客户端。收据写失败就不会发结束标记。缺失或非法的用量不能当成 0 元成功。

第一个字节都没发出去就失败、且没有收据或终态用量不确定性时，预占退回，执行状态是 `failed_no_charge`。本地预览里模型 `rc-refuse-probe` 指向一个故意不可达的地址，用来看这条路径。

### 6. 结算：`cmd/metering`

Metering 至少投递一次收据。执行编号和数据库唯一约束保证同一笔不扣两次。结算按收据里的真实 Token 扣款，并释放多出来的预占。PostgreSQL 是资金事实；Redis 只负责把事件送过去。Redis 故障后，未结算的收据可以从数据库再派发。

自动释放预占要同时满足恢复时间窗、没有可收费收据，以及原 Gateway 实例已经不在，或者执行上有明确的放弃标记。不能只因为过了一段时间就退钱。收据或异常写入失败可能只留下 `executing`。Metering 会将超过恢复窗口、没有放弃标记和可收费收据、且所属实例仍存活或心跳未知的执行，锁行复查后转入 `review_required`，保留预占并写审计；数据库故障时下轮重试。已有有效收据继续结算，迟到的有效收据也可在人工处置前恢复结算。人工核对队列见[资金恢复手册](runbooks/billing-recovery.md)。

已交付部分内容后取消或断流，若未出现收据写入失败或终态用量异常、也没有可收费收据，仍可留下放弃标记，随后按恢复规则全额释放。未知上游成本由平台承担；这有反复取消获取部分内容的成本风险，当前没有上游对账或专门的取消滥用控制。客户重试会创建新执行，`X-Request-ID` 只关联日志，不提供请求幂等。

金额是整数微元（`10^-6` 元）。流水只追加，冲正写反向流水，不改历史余额行。

## 配置怎么到网关

Console 通过 Control 修改 Provider、凭据和路由。路由按版本整份替换，并用期望版本避免盖掉并发修改。Gateway 使用已经应用的那一版。上游秘密走单独的凭据通道，不出现在普通快照、Console 响应或日志里。

Control 的配置写入按单个 writer 设计。

## 身份在业务上怎么分

用户是全局登录身份，可以有个人账户，也可以加入多个企业。个人账户没有团队成员。平台管理员和企业角色分开：管平台不会自动成为某家企业的成员。

Key 绑在创建时的账户和那一次成员关系上。调用方不能在请求里改扣费账户。成员被暂停或移除后，旧 Key 不能再发起调用；重新加入得到新的成员关系和新 Key。当月已累计的额度不因为重新加入而清零。

企业 owner 管理成员和角色。admin 只能管理普通 member。每个人只能创建和查看自己的 Key。
