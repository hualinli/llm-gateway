# 当前系统架构

本文记录 **2026-10-06，主线 `02d271a`** 的代码结构和实际数据流。它描述现有实现，不代表新业务目标已经落地。平台、企业和成员的目标行为及后续事项见[业务方案](BUSINESS.md)；关键工程决策见[技术决策](decisions.md)。实现与本文冲突时，以当前代码为准并更新本文。

## 运行组件

| 组件 | 主要职责 | 事实边界 |
|---|---|---|
| Web | 登录后的管理界面；通过同源 API 访问 Console 和 Gateway | 页面权限不是服务端授权的替代品 |
| Console | 用户、会话、组织、成员、邀请、审计和资金管理 HTTP API | 业务数据写入 PostgreSQL；Key 与路由变更经 Control API 发布 |
| Control | API Key 与 Provider 凭据的权威存储，版本化配置的唯一 writer | 向 Gateway 发布配置快照；不承担企业计费业务 |
| Gateway | API Key 鉴权、组织成员状态检查、资金准入、限流、模型代理和流式终态处理 | 请求热路径；配置来自 Control，账户与计费事实来自 PostgreSQL |
| Metering | 用量/收据消费、持久收据派发、结算、恢复、对账和账单查询 | PostgreSQL 是资金事实源；Redis 只承载事件传输 |
| PostgreSQL | IAM、Control、价格、账户、资金流水、执行与收据等持久事实 | 多服务共享数据库，但各业务表有明确 writer |
| Redis | 跨实例限流，以及 Metering 事件与收据的传输 | 不是账户余额或结算事实源 |

## 一次模型请求

```text
客户端
  → Gateway API Key 鉴权
  → PostgreSQL 权限与成员状态检查
  → PostgreSQL 计费准入和余额预占
  → Redis 限流
  → 活跃流保护
  → 上游模型路由与 SSE 代理
  → 写出成功终态前持久化用量收据
  → 客户端
```

计费准入位于限流和代理之前。准入会固定价格版本与输入/输出 Token 上界，在一个 PostgreSQL 事务中检查可用余额、创建执行记录并预占费用。余额不足、缺少价格或计费数据库不可用时，请求不会到达上游。演示配置可关闭正式计费；部署配置决定是否启用这些保护。

代理只允许在客户端收到第一个 SSE 事件前切换上游。第一个事件写出后，后续中断会结束当前流，不会自动重放请求，避免客户端收到重复内容。有效用量收据必须在 `[DONE]` 写出前提交；如果持久化失败，Gateway 不发送 `[DONE]`。

## 配置与访问控制

Console 经 Control 的管理 API 创建、撤销 Key 并发布组织策略。Control 在同一事务中保存权威记录、配置投影和审计，再通过带版本的 Get/Watch 向 Gateway 同步。Gateway 只使用已应用的内存快照；配置断线超出租约后，会拒绝新的请求。在途请求按流式请求自己的生命周期结束。

Gateway 的访问检查还会向 PostgreSQL 核实组织、成员和 Key 当前状态，避免成员或组织已停用时仅依赖旧快照放行。Key 撤销依靠版本化配置传播。Provider 上游密钥通过 Control 的加密凭据仓库解析，不进入普通配置快照。

当前 Key 的模型 allowlist 有三态：未设置表示继承，空列表表示拒绝全部，非空列表表示允许指定模型。现有模型策略并未实现[业务方案](BUSINESS.md)所要求的完整“平台为账户开放、账户成员共享”规则；成员级模型限制仍是后续 TODO。

## 计费事实与结算

一次正式计费执行有独立 ID，并记录组织、可选用户和 Key、模型、固定价格版本、预占金额与状态。主要状态如下：

```text
reserved → executing → receipt_recorded → settled
    ├──────────────→ failed_no_charge
    ├──────────────→ released
    └──────────────→ review_required
```

- `reserved` 固定价格并占用可用余额；`executing` 表示上游调用中。
- `receipt_recorded` 表示成功用量已持久化，但仍等待结算，预占继续保留。
- `settled` 在同一事务中写消费流水、释放多余预占并更新余额投影。
- `failed_no_charge` 代表失败且不向客户收费；`released` 代表带审计理由的放弃或恢复。两者都归还预占、不产生消费流水。
- `review_required` 表示用量缺失、非法或无法确认等情况，需要人工处理；自动恢复不会仅因时间经过而释放它。

Gateway 在 PostgreSQL 中提交收据后，由 Metering dispatcher 将其投递到 Redis Stream。结算消费者以至少一次方式处理；每笔消费使用稳定业务 ID 和唯一约束，重复投递不会重复扣费。Redis 故障后，未结算的 PostgreSQL 收据可重新投递。

恢复任务只处理符合恢复窗口、实例心跳/放弃标记和无可收费收据等条件的执行，并把检查依据与释放写入审计。单纯过期不足以释放资金。细节见[资金恢复手册](runbooks/billing-recovery.md)。

`billing_entries` 是追加式流水事实，`billing_accounts` 是可从流水重算的余额投影。正式账户金额以 CNY 微元记录，价格版本不可变，执行使用准入时固定的价格。旧 `metering_events` 与 `/ledger/balance` 属于演示用量口径：它们不是可充值余额，也不等于正式账单。

## 与已确认业务目标的差距

以下是当前代码事实与[业务方案](BUSINESS.md)的差异，不能把目标描述成已上线能力：

- 登录流程每次都会幂等确保用户有个人组织；新目标仍保留个人账户，并允许同一用户加入多个企业。账户选择、Key 和消费归属需要按新规则分别处理。
- 现有资金准入按组织账户余额预占，没有成员月度额度及与账户余额原子联动的成员额度预占。
- 当前企业负责人/管理员具有组织范围的 Key 列表和管理能力；新目标要求成员独立管理自己的 Key，企业管理员看不到成员 Key。
- 现有 Key 支持 Key 级模型 allowlist；新目标第一版由平台设置账户可用模型，账户成员共用，后续才加入成员级限制。
- 当前成员角色和账单能力不能替代新方案要求的负责人/管理员/成员权限边界、成员消费归属和企业/个人账户隔离。

重构允许重建开发数据库；无需兼容旧开发数据。这里的差距说明当前行为，不改变新业务方案。
