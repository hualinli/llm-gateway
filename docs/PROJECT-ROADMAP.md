# LLM Gateway 项目演进路线图

> 本文是项目未来演进的主路线和协作契约，用于指导维护者与自动化 Agent 选择任务、判断优先级、定义验收标准并保存证据。它描述“为什么做、先做什么、做到什么程度”，原则上不规定具体代码实现。

## 1. 文档目的

项目当前已经具备数据面、控制面、异步计量和可观测性的基础闭环。下一阶段的目标不是继续横向堆叠功能，而是把已经选择的核心问题做深，形成一个：

- 能用一句话解释价值的系统；
- 在故障情况下仍具有明确语义的系统；
- 每个关键承诺都能被测试和量化证据支持的系统；
- 面试官可以在较短时间内运行、观察并深入追问的项目。

本文解决四类协作问题：

1. 什么是项目的北极星问题；
2. 哪些系统不变量比新增功能更优先；
3. 各阶段的范围、依赖和退出标准是什么；
4. 人和 Agent 如何避免重复建设、局部优化与文档失真。

## 2. 项目定位

### 2.1 北极星问题

项目的核心问题定义为：

> 在上游延迟、断流、配置错误以及计量组件故障同时可能发生的情况下，如何让一次 LLM 流式请求具有明确、稳定的用户语义，并让每次成功执行都可追踪、可计量、可恢复？

这个定义刻意把重点放在“流式执行的正确性与可证明性”，而不是支持多少家 Provider、拥有多少个后台页面或部署了多少个服务。

### 2.2 面向用户的价值

对于 API 调用者，项目应提供：

- 稳定且可理解的 OpenAI-compatible 流式接口；
- 首个响应事件之前的安全故障切换；
- 首个响应事件之后不产生重复 token 的明确行为；
- 可诊断的错误、请求标识和服务状态；
- 合理的限流、超时和取消行为。

对于平台维护者，项目应提供：

- 可验证、可回滚或可拒绝的版本化配置；
- 不泄露原始凭据的 Provider 和 API Key 管理边界；
- 可恢复、可去重、可对账的计量链路；
- 能回答“发生了什么、影响多大、是否恢复”的观测证据；
- 一条短、稳定、可重复的本地演示和验证路径。

### 2.3 当前阶段不追求的目标

以下事项不是当前主线，除非它们直接服务于核心不变量或阶段验收：

- 为增加数量而增加新的 Provider adapter；
- 建设完整商业化管理后台；
- 多区域、跨云和大规模 Kubernetes 编排；
- 复杂计费套餐、支付和财务结算；
- 没有基准和容量目标支撑的微观性能优化；
- 为展示技术栈而引入新的消息队列、数据库或框架。

这些能力未来可以加入，但不得抢占正确性、可验证性和演示体验的优先级。

## 3. 设计与决策原则

### 3.1 第一性原理

每项工作先回答以下问题：

1. 用户或运维人员真正承受的失败是什么？
2. 系统必须保持的最小不变量是什么？
3. 哪个组件拥有事实源，哪个组件只是缓存或投影？
4. 失败时应拒绝、降级、重试还是继续？为什么？
5. 如何观察和证明上述行为？

不得仅以“常见网关都应该有”“看起来更生产级”作为立项理由。

### 3.2 MECE 工作分解

后续工作统一归入四个互斥的结果域：

1. **请求正确性**：客户端最终看到了什么；
2. **配置正确性**：数据面最终执行了什么；
3. **计量正确性**：成功执行最终如何入账；
4. **可验证性与交付体验**：上述承诺如何被观察、复现和理解。

安全、性能和可维护性不是独立的功能清单，而是贯穿四个结果域的质量约束。

### 3.3 量化思维

任何“更快”“可靠”“不丢”“可用”都必须被转换成可测量定义。每个阶段至少应包含：

- 一个成功率或正确率指标；
- 一个延迟或恢复时间指标；
- 一个资源或容量指标；
- 一个故障注入场景；
- 一份带环境信息、命令和原始输出的证据。

初始目标可以是项目内部基线，不必伪装成生产 SLO。目标值应在第一次基准测试后校准，而不是凭感觉确定。

### 3.4 诚实边界

- 设计目标、已实现能力和已验证结论必须分开表述；
- 单元测试通过不能替代真实依赖集成测试；
- 本地假上游结果不能表述为真实公网 Provider 容量；
- 未验证的推断必须明确标为假设；
- README、代码、运行方式和验证记录必须保持一致。

## 4. 系统不变量

不变量是所有功能开发和重构的最高约束。破坏不变量的改动，即使测试通过，也不能合并为完成状态。

### 4.1 请求正确性不变量

**R1：首事件前可以切换，首事件后绝不透明重放。**

一旦客户端收到任何已提交的 SSE 事件，Gateway 不得自动切换 Provider 并重放请求。断流应被记录为不完整流，而不是伪装成成功或重新开始一条内容流。

**R2：客户端取消必须停止无意义的上游工作。**

客户端断开或请求上下文取消后，不应继续新的 Provider 尝试，也不应继续长期占用上游连接。

**R3：错误归属稳定。**

客户端请求错误、客户端限流、网关配置错误、上游故障和内部故障应具有可区分且稳定的状态码、错误码和观测标签。

**R4：请求改写最小化。**

Gateway 只修改协议必需字段；未知 JSON 字段应被保留，不能因为内部结构体不完整而被静默删除。

**R5：资源使用有界。**

请求体、单个 SSE event、排队等待、单次尝试、流空闲时间和必要缓冲必须有明确边界。

### 4.2 配置正确性不变量

**C1：声明为 active 的配置必须可执行。**

控制面不能把“已持久化”直接等同于“已被数据面应用”。系统必须明确区分期望版本、已应用版本和拒绝版本。

**C2：配置要么完整应用，要么保留上一可用快照。**

Provider、路由和授权状态不得进入无法解释的半更新状态。安全撤销若需要优先于可用性执行，必须作为明确的例外语义记录和测试。

**C3：版本单调且可追踪。**

配置版本不能在重启、重连或并发写入时回退。每次变更都应能关联操作者、结果和失败原因。

**C4：秘密材料不跨越不必要的边界。**

原始 API Key 和上游凭据不得进入配置历史、Watch 消息、普通日志或列表响应。控制面只保存不可逆摘要或不透明引用。

**C5：配置失联策略显式。**

控制面失联后是继续使用最后快照、租约到期撤销授权，还是拒绝新流量，必须由部署策略明确决定并可观测。

### 4.3 计量正确性不变量

**M1：成功执行不能静默变成免费请求。**

缺失或非法 usage 必须进入待调查、死信或补偿流程，不能写成零费用成功记录。

**M2：同一执行重复投递只能入账一次。**

计量事件必须拥有独立、稳定的执行身份；客户端提供的关联 ID 不能直接充当全局幂等键。

**M3：不同执行不能错误合并。**

不同租户或同一客户端关联 ID 下的多次真实执行必须可区分。

**M4：确认发生在持久化之后。**

消费者只有在台账成功写入或死信成功保存后才能确认消息。

**M5：积压、丢弃和恢复可量化。**

任何内存队列溢出、spool 写入失败、重放失败、pending 积压和 DLQ 增长都必须有指标和运行手册。

### 4.4 可验证性不变量

**V1：主路径可以由一个入口启动。**

评审者不应手工管理五个终端才能看到项目价值。

**V2：关键主张可以由自动化场景重现。**

正常流、首事件前切换、首事件后断流、配置热更新、计量去重和故障恢复都应有稳定入口。

**V3：性能数字可追溯。**

每个对外性能数字都必须关联代码版本、机器环境、负载参数、上游行为和原始结果。

**V4：文档是当前事实的索引。**

README 不重复维护大量易过期状态；详细证据和设计文档应成为可链接的事实源。

## 5. 优先级模型

任务优先级使用以下维度评估，每项取 1–5 分：

| 维度 | 含义 |
|---|---|
| 用户影响 | 对请求正确性、错误体验或演示体验的影响 |
| 不变量风险 | 当前缺口造成错误、丢账或安全问题的可能性 |
| 面试辨识度 | 是否能体现系统设计深度和工程判断 |
| 证据增益 | 是否增加可重复测试、数据或故障证据 |
| 成本 | 开发、验证和维护成本，分数越高成本越大 |

建议排序分数：

```text
优先级 = 2 × 不变量风险 + 用户影响 + 面试辨识度 + 证据增益 - 成本
```

公式只用于帮助比较，不替代工程判断。任何明确破坏系统不变量的问题自动进入最高优先级。

## 6. 总体路线

路线分为五个阶段。阶段按依赖排序，允许同一阶段内并行，但不建议跳过退出标准去扩展下一阶段功能。

| 阶段 | 核心结果 | 主要解决的问题 |
|---|---|---|
| Phase 0 | 建立基线与事实源 | 我们现在到底能证明什么 |
| Phase 1 | 配置闭环可信 | 控制面成功是否等于数据面可执行 |
| Phase 2 | 请求与计量故障语义闭环 | 请求成功、断流、计量之间是否一致 |
| Phase 3 | 一键演示与持续验证 | 其他人能否快速、稳定地复现价值 |
| Phase 4 | 量化性能与容量边界 | 网关成本和失效拐点在哪里 |
| Phase 5 | 面试交付与选择性扩展 | 如何形成清晰故事并决定后续功能 |

## 7. Phase 0：基线与事实源

### 7.1 目标

建立统一的当前状态、测试分层和文档入口，消除“代码已经完成，但 README 仍写待做”一类事实冲突。

### 7.2 工作范围

- 为现有能力建立清晰清单：已实现、已测试、已集成验证、尚未验证；
- 区分单元测试、本机网络测试、依赖集成测试、端到端测试和性能实验；
- 建立基础 CI，至少运行格式、静态检查、普通测试和竞态检测；
- 固定本地依赖镜像的大版本或确定版本，避免 `latest` 造成不可重复结果；
- 将 README 缩减为项目入口，把设计、运行手册和实验结果分流到独立文档；
- 建立变更证据目录与命名约定。

### 7.3 退出标准

- 新环境可以根据文档得到相同的构建和普通测试结果；
- CI 对主分支和变更分支执行一致的基础质量门禁；
- README 中不存在相互冲突的“已完成/待完成”描述；
- 每个外部依赖集成测试都明确说明启用条件和跳过原因；
- 生成一份基线报告，记录当前覆盖率、测试数量、已知限制和验证日期。

### 7.4 建议证据

- CI 成功记录；
- 测试和 race detector 原始输出；
- 分包覆盖率报告；
- 固定版本的依赖清单；
- 基线报告及对应提交号。

## 8. Phase 1：配置闭环可信

### 8.1 目标

让配置从“写入成功”升级为“状态明确、可执行、可诊断”。这是当前最高优先级阶段。

### 8.2 必须回答的产品语义

1. 管理 API 返回成功时，究竟表示已持久化、已广播，还是已被 Gateway 应用？
2. 一个 Gateway 拒绝配置时，控制面和操作者如何得知？
3. 多个 Gateway 应用状态不一致时，哪个版本算 active？
4. 路由引用不存在的 Provider 时，应在何处拒绝？
5. 某台 Gateway 无法解析本地凭据引用时，是全局配置失败还是实例局部失败？
6. 安全撤销与路由可用性冲突时，优先级如何定义？

### 8.3 工作范围

- 定义配置生命周期，例如 desired、validating、active、rejected、superseded；
- 定义控制面结构校验与 Gateway 本地环境校验的责任边界；
- 补齐路由、Provider 和凭据引用之间的跨字段一致性规则；
- 记录各 Gateway 的已应用版本、最近拒绝版本、时间和原因；
- 为配置更新提供清晰的操作结果，而不是只返回持久化版本；
- 将 readiness 与是否拥有可执行配置关联；
- 保留上一份可用快照，并明确安全撤销的特殊处理；
- 建立配置变更审计和版本差异的可读输出。

### 8.4 验收场景

- 合法配置从提交到 Gateway 生效，全链路版本一致；
- route 引用不存在的 Provider 时，在不会制造“假 active”的阶段被拒绝；
- Provider URL 非法时，旧快照继续服务且拒绝原因可查；
- Credential reference 在某 Gateway 无法解析时，该实例状态可见；
- Watch 丢失或断线后，通过补拉追上最新可用版本；
- 旧版本或并发写入不会覆盖新版本；
- 租约到期与恢复后的授权行为符合文档定义；
- 配置错误不会静默创建 Mock 或把流量发往意外目标。

### 8.5 量化指标

- 配置提交到全部目标 Gateway 应用的延迟分布；
- 当前 desired/applied 版本差；
- 配置拒绝总数及原因分类；
- 使用过期配置的 Gateway 数量；
- 配置同步断开持续时间；
- 租约过期和恢复次数。

### 8.6 退出标准

- “配置成功”的语义在 API、指标、日志和文档中一致；
- 不可执行配置不会被展示为已全面生效；
- 所有验收场景都有自动化测试；
- readiness 能区分进程存活与配置可服务；
- 演示中可以主动制造错误配置并清楚观察拒绝、旧版本保留和恢复过程。

## 9. Phase 2：请求与计量故障语义闭环

### 9.1 目标

证明一次流式执行从客户端请求到最终入账具有一致语义，尤其是在断流、组件不可用和重复投递时。

### 9.2 请求正确性工作流

- 建立正式错误分类表，覆盖客户端错误、限流、未知模型、上游拒绝、上游超时、网关内部错误和已提交后的断流；
- 明确首事件的定义和响应提交点；
- 验证连接、TLS、响应头、首事件、流空闲和总尝试超时的边界；
- 明确慢客户端的背压策略和资源上限；
- 为客户端取消、半关闭和网关优雅退出建立测试；
- 明确未知模型、无可用 Provider 和全部 Provider 失败时的用户语义；
- 让错误响应包含稳定错误码和请求关联信息。

### 9.3 计量正确性工作流

- 固化 event identity、client request identity 和 trace identity 的区别；
- 定义哪些执行结果应生成计量事件，哪些进入不完整或待补偿状态；
- 验证队列满、Redis 不可用、spool 满盘、进程异常退出和恢复重放；
- 验证 Consumer 重复投递、pending 接管、数据库失败和 DLQ 写入失败；
- 建立对账结果的差异分类，而不仅是总数比较；
- 明确数据保留、spool 上限、DLQ 上限和人工处置入口；
- 使“成功响应但 usage 缺失”成为显式异常，而非零费用记录。

### 9.4 端到端状态矩阵

至少覆盖以下组合：

| 客户端观察 | 上游结果 | 计量状态 | 预期结论 |
|---|---|---|---|
| 未收到事件 | 主上游超时，备用成功 | 正常入账 | 安全切换 |
| 已收到事件 | 上游中途断流 | 不完整/待处理 | 不重放，不伪装完整成功 |
| 完整收到 `[DONE]` | usage 正常 | 正常入账 | 完整成功 |
| 完整收到 `[DONE]` | usage 缺失 | DLQ/待补偿 | 不静默免费 |
| 客户端主动断开 | 上游被取消 | 按定义处理 | 不继续新尝试 |
| 完整成功 | Redis 暂时不可用 | spool 后恢复 | 最终入账 |
| 完整成功 | 事件重复投递 | 单次入账 | 幂等成立 |

### 9.5 量化指标

- 请求成功率、首事件前失败率、首事件后断流率；
- TTFT 和总耗时 P50/P95/P99；
- Provider 切换率与按原因分类的尝试数；
- 活跃流、排队时间和取消传播延迟；
- 计量入队失败、spool 字节数、重放延迟和 DLQ 增长；
- 请求完成到台账可见的最终一致性延迟；
- 重复事件去重数量和对账差异数量。

### 9.6 退出标准

- 状态矩阵中的每个组合均有自动化验证；
- 故障发生时不会出现无指标、无日志、无最终去向的请求；
- kill -9、Redis 短暂故障和 PostgreSQL 短暂故障后可以给出恢复证据；
- 能明确回答“客户端成功但最终未入账”的最大风险窗口；
- 慢客户端与超大事件不会导致无界内存增长。

## 10. Phase 3：一键演示与持续验证

### 10.1 目标

让不了解仓库的人在 5 分钟内看到核心价值，并让维护者以同一套入口重复验证。

### 10.2 黄金路径

项目应提供三个稳定入口，具体命名可以调整，但职责必须清楚：

```text
demo-up     启动完整、隔离、可检查的本地环境
demo-smoke  执行核心成功和故障场景并输出摘要
demo-down   安全停止；数据删除必须是独立显式操作
```

黄金路径不得要求使用者手工协调多个终端，也不得依赖未记录的本机环境变量。

### 10.3 Smoke 场景

- 环境和 schema readiness 检查；
- 正常 SSE 请求；
- 主 Provider 首事件前失败并切换备用；
- 首事件后断流且不重放；
- 配置热更新后无需重启即可改变路由；
- 错误配置被拒绝，旧版本继续工作；
- usage 最终进入 Ledger；
- 重复计量事件不会重复扣费；
- 关键指标和请求 ID 可以被查询。

### 10.4 用户体验要求

- 失败提示说明哪一层失败以及下一步如何检查；
- 启动过程显示组件 readiness，而不是只显示进程存在；
- 示例命令不要求把秘密写入仓库或 shell 历史；
- 数据清理与普通停止分开，避免误删卷；
- 默认端口冲突、缺少 Docker、迁移未执行等常见问题有明确提示；
- 演示输出既适合人读，也能被 CI 保存为证据。

### 10.5 退出标准

- 全新环境按 README 的最短路径可以完成 Demo；
- CI 中至少有一条依赖集成或端到端流水线；
- smoke 失败时能够定位到具体场景和组件；
- 演示结果包含版本、时间、环境和关键指标；
- 不再需要用五个手工终端证明基础闭环。

## 11. Phase 4：性能、容量与故障实验

### 11.1 目标

回答三个问题：Gateway 增加了多少成本、容量边界在哪里、故障时退化成什么样。

### 11.2 实验设计原则

- 将上游服务时间与 Gateway 开销分离；
- 同时报告直连基线和经过 Gateway 的结果；
- 控制 TTFT、token 间隔、响应长度和并发数；
- 区分闭环并发与固定到达率；
- 记录预热、持续时间、采样窗口和失败率；
- 至少重复三轮，报告波动而非只挑最佳值；
- 性能优化前先用 profile 证明瓶颈。

### 11.3 核心实验

1. **透明代理成本**：直连假上游与经过 Gateway 的 TTFT、总耗时、CPU 和内存差异；
2. **并发容量**：逐步增加并发流，找到延迟和错误率明显恶化的拐点；
3. **慢客户端**：固定上游速度、降低下游读取速度，观察内存和连接行为；
4. **Provider 故障**：注入 429、5xx、首事件超时、断流和并发上限；
5. **Redis 故障**：分别观察限流 fail-open 和计量 spool 行为；
6. **PostgreSQL 故障**：观察 Consumer pending、恢复时间和最终一致性；
7. **控制面失联**：观察配置年龄、租约行为和 readiness；
8. **优雅退出**：观察在途流完成率、强制取消数和未 flush 计量事件。

### 11.4 报告最小字段

- Git commit、Go 版本、操作系统和硬件；
- 依赖镜像及版本；
- 完整负载参数和上游行为；
- 请求数、并发数、持续时间和预热方式；
- TTFT、总延迟、失败率、吞吐、CPU、内存、GC；
- 计量积压、恢复时间和数据差异；
- 原始结果位置与生成命令；
- 结果解释、限制和下一步假设。

### 11.5 退出标准

- README 中出现的所有性能数字都有可追溯报告；
- 至少完成一份正常容量报告和一份故障恢复报告；
- 能指出当前第一个容量瓶颈并用 profile 支持结论；
- 能说明性能结论适用和不适用的环境；
- 形成下一阶段是否优化的量化决策，而不是凭直觉重构。

## 12. Phase 5：面试交付与选择性扩展

### 12.1 目标

把工程成果压缩成清晰、可信、可深入追问的项目叙事，并根据证据决定是否扩展产品能力。

### 12.2 面试交付物

- 一页项目概览：问题、架构、四类不变量、关键数字和限制；
- 一张架构图：请求、配置和计量三条链路；
- 一份 5 分钟演示脚本；
- 两个深度案例：建议选择 SSE 重试边界和计量恢复；
- 一份故障实验报告；
- 一份性能基准报告；
- 一份设计取舍记录：为什么当前不做 hedging、Kafka 或更多 Provider；
- 一组可诚实回答的已知限制和下一步路线。

### 12.3 功能扩展决策门槛

只有满足以下条件，才建议加入 Anthropic、模型目录、租户模型权限或更完整的管理后台：

- Phase 1–4 的核心退出标准已经满足；
- 新能力能展示新的系统问题，而不是重复现有 adapter 工作；
- 有清晰用户场景和验收指标；
- 不会显著扩大尚未治理的安全或一致性边界；
- README 和演示仍能保持简洁。

## 13. 横切质量要求

### 13.1 可维护性

- 包边界应跟随责任和故障域，而不是跟随文件数量；
- 控制面数据结构不能渗透到 Provider 核心领域；
- 默认值、错误分类和状态枚举应有单一事实源；
- 生产路径不应存在静默 Mock、静默内存回退或隐式 schema 变更；
- 注释解释原因、边界和不变量，不复述代码；
- 新抽象必须由至少两个真实使用场景或明显测试收益证明。

### 13.2 安全

- 本地 Demo 的宽松默认值必须与生产模式显式隔离；
- 管理面、控制面和调试端点应有明确暴露边界；
- pprof、配置、审计和指标中不得泄露秘密；
- 镜像、依赖和协议版本应可追踪；
- 安全失败应优先可观察，不能只记录一条普通日志。

### 13.3 用户体验

- 未知模型应返回可行动错误，而非模糊的上游失败；
- 每个错误响应应能关联请求 ID；
- readiness 必须反映能否处理核心请求；
- 管理操作应区分“已接受、已持久化、已应用”；
- 示例应默认走安全、成功概率最高的路径；
- 破坏性操作必须显式命名和说明影响。

### 13.4 测试策略

采用分层而非单一覆盖率目标：

| 层级 | 目标 |
|---|---|
| 单元测试 | 错误分类、状态转换、边界解析和纯逻辑 |
| 组件测试 | HTTP/gRPC、超时、取消、并发和持久化适配器 |
| 依赖集成测试 | Redis、PostgreSQL、迁移、pending、幂等和恢复 |
| 端到端测试 | 请求、配置、计量三条链路组合行为 |
| 故障实验 | kill -9、断网、超时、满队列、慢客户端和恢复 |
| 性能实验 | 基线、拐点、资源消耗和回归 |

覆盖率只用于发现盲区，不作为唯一质量目标。关键不变量即使只涉及少量代码，也必须拥有跨组件测试。

## 14. Agent 执行协议

### 14.1 领取任务前

Agent 必须先明确：

- 任务属于四个结果域中的哪一个；
- 它保护或完善哪个系统不变量；
- 当前事实和已有测试是什么；
- 是否存在重叠任务或未提交变更；
- 完成时需要提交什么证据。

如果无法回答这些问题，应先做调查任务，不直接实施大范围改动。

### 14.2 任务描述模板

```text
问题：用户或系统当前会遭遇什么失败？
所属结果域：请求 / 配置 / 计量 / 可验证性
保护的不变量：例如 C1、M2
范围：本任务包含什么
非范围：本任务明确不做什么
验收场景：正常、边界和失败场景
量化指标：完成后新增或改善什么数字
证据：测试、日志、报告或截图的保存位置
文档影响：需要更新哪些当前事实
```

### 14.3 实施约束

- 优先完成一条垂直闭环，不同时铺开多个半成品；
- 不顺手加入无关重构或新功能；
- 外部可见语义改变必须同步更新测试和文档；
- 新配置项必须有默认值、非法值行为和可观测状态；
- 新失败路径必须决定 retry、reject、degrade 或 fail-open/fail-closed；
- 不以扩大抽象层级代替解决当前具体问题；
- 不删除现有验证证据，过期证据应标记适用版本或归档。

### 14.4 完成定义

一个任务只有同时满足以下条件才算完成：

- 目标行为已实现；
- 正常、边界和失败路径得到验证；
- 相关竞态或并发风险已检查；
- 新行为有必要的指标、日志或状态输出；
- 文档与代码事实一致；
- 没有把已知风险隐藏为“后续优化”；
- 验证命令和结果可由另一位维护者或 Agent 重现。

### 14.5 交接格式

每次交接应简要说明：

1. 改变了什么用户或系统行为；
2. 哪个不变量得到加强；
3. 运行了哪些验证，结果如何；
4. 哪些内容没有验证；
5. 新增了哪些风险或后续任务；
6. 证据文件和关键代码位置。

## 15. 推荐任务队列

以下顺序是当前建议，不代表必须由一个 Agent 串行完成。

### P0：立即处理

1. 定义 desired、applied、rejected 配置语义；
2. 补齐 routes/providers 的跨字段一致性校验；
3. 建立 Gateway 配置应用状态与拒绝原因；
4. 拆分 `/livez` 和 `/readyz`；
5. 修正文档中管理面鉴权、凭据和当前完成度的冲突描述；
6. 建立基础 CI 并固定关键依赖版本。

### P1：形成可靠闭环

1. 建立请求错误分类和稳定错误码；
2. 完成慢客户端、客户端取消和首事件后断流测试；
3. 完成 spool 满盘、kill -9 与恢复验证；
4. 完成 Consumer pending、DLQ 和数据库故障恢复矩阵；
5. 建立请求完成到最终入账的端到端测试；
6. 建立配置、请求和计量的核心告警指标。

### P2：交付体验

1. 一键启动、smoke 和停止；
2. 端到端 CI；
3. 精简 README 并建立文档索引；
4. 输出基线报告与故障实验报告；
5. 建立 5 分钟演示脚本。

### P3：量化与扩展

1. 完成直连对比和并发容量实验；
2. 完成慢客户端与依赖故障实验；
3. 根据 profile 做有证据的性能优化；
4. 在核心退出标准满足后评估第二 Provider、模型目录和租户模型权限。

## 16. 路线健康度检查

每完成一个阶段或每两周进行一次路线审查，回答：

1. 当前最严重的风险仍然属于核心问题吗？
2. 最近完成的工作是否改善了某个不变量？
3. 是否出现功能数量增长但证据没有增长？
4. 是否有 README 主张无法由自动化场景证明？
5. 是否有两个组件对同一状态给出不同答案？
6. 是否能在 5 分钟内向新评审者展示当前最强能力？
7. 当前性能瓶颈是测出来的还是猜出来的？
8. 下一阶段是否可以删除、推迟或合并某些工作？

如果连续两次审查都无法指出新增的可验证结果，应暂停功能扩展，优先修复路线、验收标准或实验能力。

## 17. 最终完成标准

当项目达到以下状态，可以认为已经达到高质量面试项目标准：

- 核心问题和边界能在一分钟内解释清楚；
- 数据面、控制面和计量面各有明确不变量；
- 配置成功、请求成功和计量成功的语义不混淆；
- 关键故障场景可以自动注入并产生可读结果；
- 有普通测试、竞态检测、依赖集成和端到端 CI；
- 有可复现的性能数据，而不是目标数字；
- 新用户可以在 5 分钟内跑通黄金路径；
- README 简洁、准确，没有把规划写成实现；
- 能主动展示一个失败案例、解释设计取舍并给出恢复证据；
- 已知限制清晰，并且下一步由数据和风险驱动，而非由功能清单驱动。

达到这一标准后，项目不需要假装是完整商业产品。它的价值在于：围绕一个困难而真实的问题，做出了边界清楚、行为可证、取舍成熟的工程系统。
