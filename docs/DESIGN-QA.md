# 设计问答清单

按简历上能讲清楚的设计来准备。每题按「现在怎么做、为什么这样、边界在哪」来答。函数名、类型、文件路径，面试官看不到，不放进答案。操作步骤见[开发说明](DEVELOPMENT.md)，想对照实现再看[架构](ARCHITECTURE.md)。

还没做的不要说成已经做了：成员级模型列表、生产双向证书、真实付费上游、长时间运行、生产备份恢复。

## 1. 项目总览

### 基础问题

1. 这个项目解决什么问题？

答：它是一套 OpenAI 兼容的模型网关，加上管理台。调用方拿一把 Key 打流式接口。网关认 Key、核对组织和成员是否仍然有效、限流，并按余额和月额度先冻结一笔上限，再把流式响应转给上游，最后按实际 Token 持久扣费。管理台管人、企业、模型范围、路由、价格和账单。要讲清楚的是两件事：一次调用能不能发生，以及这笔钱怎么落成可核对的账。

2. 系统分成哪几块，数据归谁？

答：界面只展示和提交操作。管理服务写身份、成员、额度和账务查询。配置服务是路由和凭据引用的唯一写入者。网关用已经发布的配置做准入和转发，并读账户与计费事实。结算服务消费用量收据、扣款、释放多冻的金额。PostgreSQL 是账本。Redis 只做限流令牌和事件传递。

3. 一次对话补全经过哪些步骤？

答：先认 Key，再核对组织和成员，再限流，再检查这个组织同时进行的流有没有超限，然后冻结金额，最后转发。不花钱就能拒绝的请求停在冻结之前。通过之后按已发布路由转发。流的结束标记发给客户端之前，先把用量收据写入数据库。结算服务再按真实 Token 扣款，并释放多冻的部分。同一条链路也服务另一种流式补全接口。列出模型的接口只认 Key、核对身份和限流，不冻结资金，也不占流式并发名额。

4. 最值得讲的三个设计点是什么？

答：第一，认 Key 和核对成员分开。内存里只保存 Key 的哈希，用来快速判断这把 Key 在不在；组织、用户、成员是否仍然有效，以数据库为准。第二，钱在进上游之前按上限冻结，在写出结束标记之前落下收据，结算按执行编号幂等。第三，主备只发生在还没向客户端写出第一个字节的时候；已经写出内容就不能重放。

### 追问

1. 两分钟怎么讲？

答：先说它是带持久计费的模型网关。再讲一条链：认 Key、查库核对成员、限流、冻结上限、转发、收据先于结束标记、再按实际用量结算。最后讲三个取舍：内存快照可以热更新，但不能代替成员是否仍在企业里；冻结的是上限，结算才是账单；主备只发生在客户端还没收到内容的时候。

2. 为什么不放进一个进程？

答：配置发布、在线转发、资金结算的失败方式和扩容方式不同。配置按单写者发布。网关要低延迟转发，可以水平扩展。结算可以晚一点消费收据。它们共享同一套数据库，每类业务记录有明确的写入方，避免两个服务各写一套执行记录。

3. 访问量上来先看什么？

答：先看拒绝发生在冻结之前还是之后。认 Key 失败、成员不允许、限流，都不写资金记录。冻结之后的上游变慢，以及整个进程的流数量打满，会留下执行记录。网关扩成两个进程时，每个进程各有一份组织并发上限，实际并发大约是配置值的两倍。跨进程真正共享的只有 Redis 里的令牌桶。

## 2. 认 Key

### 基础问题

1. 为什么不在每次请求时用明文去数据库认 Key？

答：内存快照的键是 Key 的哈希，里面没有明文。配置更新时整份快照替换。这一步只回答「这把 Key 在当前已发布的快照里有没有」。对不上就拒绝，后面的限流和转发都不会跑。快照不保存明文；处理请求时，网关仍会在内存中接触 Authorization 里的明文，不把它写入日志。

2. 停用一把 Key 之后，调用方看到什么？

答：停用的 Key 不会留在新快照里。调用方看到的和从未存在过的 Key 一样，都是未授权。更细的原因只留在服务端日志里，避免用不同文案告诉别人这把 Key 曾经存在过。

3. 快照认过 Key，人已经被移出企业，请求会怎样？

答：认 Key 仍可能通过。下一步会用同一把 Key 的哈希再读数据库，核对的是创建这把 Key 时绑定的那一次成员关系。对不上就拒绝。快照负责快速认出 Key 和热更新，成员是否仍然有效以数据库为准。

### 追问

1. 为什么成员关系不能只信内存快照？

答：人可以被移出、停用或重新加入，这些变化不需要等下一份路由快照。若只信内存，一把已经失效的 Key 会继续花钱。所以认 Key 和「现在还许不许他发起调用」分成两步。

2. 调用方能不能指定这次扣哪个账户？

答：不能。Key 在创建时绑定账户，以及创建当时的那一次成员关系。网关用这个绑定决定扣谁的钱。允许请求里再传一个账户，就会变成拿一把 Key 花另一个账户的余额。

## 3. 这次调用还允不允许

### 基础问题

1. 认完 Key 之后还要查什么？

答：查这把 Key、它所属的组织、对应用户，以及创建 Key 时记下的那一次成员关系是否仍然有效。角色也要允许发起调用。查的是创建时的那一次成员关系，不是这个人后来重新加入产生的新关系。

2. 数据库暂时查不到，为什么拒绝而不是放行？

答：放行等于用一份可能过期的快照决定能不能花钱。连接失败、超时、提交失败都拒绝，并告诉客户端准入暂时不可用。库里根本没有这把 Key，则是未授权，那是业务拒绝，不是数据库故障。

3. 重新加入企业后，旧 Key 为什么不能继续用？

答：再次加入会生成一次新的成员关系。旧 Key 仍钉在原来那一次上，对不上就拒绝。当月已经累计的用量也不因重新加入清零。

### 追问

1. 客户端为什么看不到「组织已停用」这种原因？

答：对外只有两类说法：凭据无效，或者身份有效但不允许发起调用。具体原因只进日志。这样调用方无法靠不同文案探测组织、用户或 Key 的内部状态。

2. 未授权、禁止、暂时不可用，在这一层分别表示什么？

答：未授权表示这把 Key 不为当前事实所承认，例如已经过期、没有组织归属、库里没有，或状态不对。禁止表示 Key 还在，但组织、用户、成员或角色不允许发起调用。暂时不可用表示核对本身失败，这次请求没有被判定为允许。

## 4. 能用哪些模型

### 基础问题

1. 模型范围为什么不能只用「有列表」和「没列表」？

答：每一级要能表达三种意思：沿用上一级、这一级明确谁都不能用、这一级只能用列出的模型。把「空」同时当成「不限制」和「全部拒绝」，两种意思就分不开。

2. 范围怎么叠加？

答：平台目录、组织、成员、Key，从宽到窄。下一级只能把上一级收得更窄，不能放大。只要某一级设了限制，就要读请求里的模型名。目录里没有的模型按不存在拒绝；目录里有、但不在允许范围内，按禁止拒绝。

3. 成员级限制现在做到哪一步？

答：叠加规则里留了成员这一层，当前读出来始终是「沿用组织范围」。第一版是账户内成员共用账户可用的模型。不能说成员级限制已经可用。

### 追问

1. Key 上的列表为什么还要和数据库里的列表再比一次？

答：数据库里是这把 Key 自己的权威列表，内存快照是推送过去的副本。两边取更窄的一边，刚收紧的限制马上生效。一份偏旧的快照不能把权限放大。

2. 请求根本不是流式时，为什么不在这一步就报协议错误？

答：这一步只判断「如果这次调用会到达上游，模型是否允许」。协议不支持、请求体损坏、体积过大，由转发按接口契约拒绝。身份核对不去抢那个错误。

## 5. 限流

### 基础问题

1. 限流为什么放在冻结金额前面？

答：被限流的请求不需要碰钱。先扣 Redis 令牌，再占本进程里这个组织的流名额。失败就不写执行记录。数据库不会被明显会被拒绝的流量写满。

2. 两个并发上限有什么差别？

答：组织同时进行的流，在冻结金额之前检查，超出是限流，账上没有这笔执行。整个进程能同时承载的流，在转发内部、冻结之后检查，超出是暂时不可用，因此会留下执行记录，冻结的金额随后释放。这是已知的顺序取舍。

3. 网关开多个进程时，哪些限制会被放大？

答：每个进程各有一份组织流上限和全局流上限，两个进程的实际并发大约是配置的两倍。跨进程真正共享的是 Redis 里按组织计数的令牌桶。

### 追问

1. Redis 不可用时怎么选？

答：可以做成失败放行，也可以做成失败拒绝。生产要明确选一个，不能沿用演示环境的默认。失败拒绝会把依赖故障变成暂时不可用。失败放行会在 Redis 故障时失去跨进程限流。

2. 组织没有单独的限流策略时怎么计？

答：按租户计，不再叠加一层组织桶。组织归属来自前面已经核对过的身份，不来自调用方自己填的参数。

## 6. 冻结、收据与结算

### 基础问题

1. 为什么先冻结再调上游？

答：余额和月额度要在并发调用下一起判断。冻结的是「这次最多可能花多少」。上游返回的真实 Token 通常更少，结算时按实际费用扣，多冻的释放。若等上游结束再看余额，两个请求可以同时看中同一笔钱。

2. 冻结金额为什么不是最终账单？

答：冻结按完整请求字节数加模板开销估计输入上限，再加固定的输出上限。JSON Schema 也包含在输入里；未知扩展、工具和多模态不放行。这套上限依赖上游遵守输出限制和 tokenizer／模板假设，不能直接推广到任意兼容服务。结算只用真实的输入和输出 Token，以及准入当时钉死的价格版本。之后改价不改变这一笔。常见情况是冻结了几千微元，实扣几十微元，差额是没生成的那部分上限。

3. 用户的钱其实够两次实际调用，为什么第二次会马上被告知余额不足？

答：第二次看的是「账面余额减去仍被冻住的上限」，不是「账面余额减去第一次最终会扣的那一点」。第一次还没结束时，上限还占着。第二次自己的上限若超过剩余可用金额，立刻拒绝，不进上游，也不干等第一次结束。账户行上的锁只维持在这一次冻结事务里。第一次结算把多冻的释放之后，第二次才能再通过。把单次输出上限设小，冻结也会变小。

4. 为什么收据必须在结束标记之前落库？

答：结束标记表示这次流可以按已知用量结清。先发给客户端再写收据，进程在中间死去，客户端认为成功，账上却没有依据。写收据失败就不发结束标记。用量缺失或自相矛盾，不能当成零元成功。

5. 结算可能收到重复消息，怎么避免扣两次？

答：每次调用在准入时就有一个执行编号。收据按这个编号唯一。结算事务按这个身份幂等。Redis 丢了，可以靠数据库里已经写下的收据再投递。Redis 不是账本。

6. 金额为什么用整数微元？

答：内部以百万分之一元的整数记账，接口上用十进制字符串。不用浮点数。流水只追加。更正写一笔反向流水，不改历史流水，也不直接改余额就算更正。

### 追问

1. 一个字节都没写给客户端就失败了，钱怎么处理？

答：确认没有产生可计费输出时，冻结的金额全部退回，记成未计费失败。故意把某个模型指到不可达地址，就是为了把这条路径留成明确失败，而不是悄悄换成别的上游。

2. 什么时候不能因为超时就自动退？

答：只因为过了时间不够。还要确认没有可收费的收据，并且能证明原来的网关进程已经不在，或者这笔执行上有明确的放弃标记。收据或异常记录写入失败时，可能暂留在执行中。数据库恢复后，后台会把超过恢复窗口、无放弃标记和可收费收据、实例仍存活或心跳未知的执行转入人工核对，冻结继续拿着；已落库的有效收据仍走结算。核对队列的超时只用来提醒人，不自动动钱。

3. 成员月额度降为 0，已经在进行的请求呢？

答：新调用会被拒绝。已经准入的请求继续按准入时的月份和价格结算。额度按北京时间的自然月归集，迟到的结算不改月份。

4. 几类资金操作为什么要规定加锁顺序？

答：冻结时锁账户。写收据时先锁这笔执行。结算时先锁收据，再锁执行，再写流水。恢复时先锁执行。收据已经成功写下之后，恢复不能再把这笔释放掉。释放已经成功之后，也不能再补一张成功收据。顺序相反会互相等待，或者让同一笔钱走出两个结果。

## 7. 转发

### 基础问题

1. 为什么只接受流式？

答：对外契约是流式输出。非流式若伪装成一段流，调用方无法区分「模型没说话」和「协议不支持」。请求里没写流式，也按非流式拒绝。

2. 主备的边界是什么？

答：一个模型可以配置一串上游，按顺序试。当前上游返回服务器错误、超时或连不上，并且响应还没写出第一个字节，就试下一个。参数错误这类换一家也会错的失败，停止重试。已经写出字节就断流，不把同一段请求重放一遍，否则客户端会把两段答案拼在一起。

3. 换了备用上游，会不会扣两次？

答：不会。执行编号在准入时生成，网关内换上游仍是同一次执行。客户端重新发起请求会生成新执行，可能再次生成和收费；请求关联编号不提供幂等。备用上游成功时，收据只写一次。已经进入终态的执行，也不会再开一次付费生成。

### 追问

1. 客户端中途断开呢？

答：不再尝试下一个上游，也不往已经断开的连接上补一段错误说明。已经写出的不完整流单独计数，不记成成功完成。即使已经交付部分回答，只要没有可收费收据、收据写入失败或终态用量异常，也会记录放弃标记，等待恢复窗口后按规则释放全部冻结。未知上游成本由平台承担，反复取消可能造成成本损失，当前没有专门的取消滥用控制。

2. 进程流数量打满，和上游不可用，调用方怎么区分？

答：前者是本进程保护，返回暂时不可用，而且因为发生在冻结之后，账上会有执行记录和随后的释放。后者若发生在第一个字节之前，是网关错误，冻结退回。限流则是另一类拒绝，账上没有这笔执行。

## 8. 配置与密钥

### 基础问题

1. 路由为什么按版本整份替换？

答：一份路由表示「这个模型由哪些上游、按什么顺序负责」。局部修改容易和并发修改交织。写入时带上期望的当前版本，版本不符就拒绝覆盖。网关只用已经应用成功的那一版。

2. 上游密钥为什么不放进下发给网关的配置？

答：这份配置会热更新进网关内存，也更容易进日志和调试接口。配置里只放凭据引用。凭据加密保存在数据库。Gateway 应用配置时解析引用，并在 Provider 实例内存中保存供后续上游调用使用；明文不进入普通配置快照和日志。

3. 谁可以改路由？

答：配置服务是唯一的权威写入者。管理台是操作入口，不是第二份路由真相。两个入口同时改同一份路由会互相覆盖。

### 追问

1. 上游密钥怎么轮换？

答：先创建新凭据，再把供应商指到新凭据，确认网关已经用上，最后撤销旧的。仍被当前配置引用的凭据不能撤销。撤销不删除历史流水和审计。

2. 生产环境的管理通道为什么要双向证书？

答：配置写入和凭据解析比普通调用更敏感。本地演示可以明文。生产启动时会拒绝缺少证书的配置，也会按值拒绝仓库里的演示令牌。这件事在设计上是启动条件，还没有在生产环境验证过，面试时要说成要求，不能说成已经上线验证。

## 9. 身份与 Key 归属

### 基础问题

1. 用户、个人账户、企业成员、平台管理员是什么关系？

答：用户是登录身份。个人账户和企业账户的钱、Key、账单分开。一个人可以同时有个人账户和多个企业里的成员关系。平台管理员不是企业角色，管平台不会自动变成某家企业的成员。

2. 企业里谁能看见别人的 Key？

答：不能。所有者和管理者可以看成员用量，不能看别人的 Key 标识、名称、前缀和秘密。每个人只能创建和停用自己的 Key。管理者只能管理普通成员，不能改其他管理者或所有者。

3. 企业余额不够时，能不能扣这个人的个人钱包？

答：不能。两个账户的资金互相独立。成员花的是企业余额。月额度只是这个人在企业里的当月上限，不是第二个钱包。

### 追问

1. 暂停成员和停用 Key 有什么差别？

答：暂停成员会让他在这个企业下的 Key 都不能发起新调用，历史消费还在。停用针对的是某一把 Key。两种都不是把流水删掉。

2. 所有者、管理者、普通成员，管理范围差在哪？

答：所有者管理角色。管理者只能管理普通成员。普通成员看自己的 Key 和自己的用量。平台管理员处理的是平台级操作，不会因此获得某家企业的成员身份。

## 10. 这些规则怎么被钉住

### 基础问题

1. 不连真实上游、不连真实账本时，能确认什么？

答：能确认顺序和失败边界。被限流或组织并发打满时，冻结次数不能增加。非流式会被拒绝。第一个字节之前可以换备用上游。已经确定会失败的错误不再换。已经写出内容的不能重放。结束标记发给客户端之前，必须先走过写收据这一步。成员、组织、角色的各种拒绝，也可以用造好的事实逐条核对。

2. 为什么这些检查要打在真正上线的那条链路上？

答：单独复制一份顺序来测，以后有人把限流挪到冻结后面，检查仍会通过。拒绝码和「没花钱」这些不变量要钉在真正对外服务的那条链上。

3. 必须连数据库才能确认的是什么？

答：冻结、同一笔不重复扣款、用量异常时不按零元结清、结束标记前收据已经写下，以及身份和权限。内存里的假账本替代不了「两个事务会不会扣重」和「唯一约束是否生效」。

### 追问

1. 怎么说明「被限流的请求没有冻住钱」？

答：让第一笔请求进入上游并占住该组织的流名额，第二笔被限流。冻结次数必须仍是一。这是在钉顺序，不是在做压测。

2. 怎么说明换上游不会产生第二笔账单？

答：同一次执行只允许一张收据。第一个字节之前的失败还不写收据；成功的那一次才写。要看的是写收据的次数和执行身份，不是页面上能不能看到字。

## 11. 综合追问

1. 你做过的一个不能倒过来的顺序是什么？

答：不花钱的拒绝放在冻结之前，收据放在结束标记之前，结算放在独立进程。倒过来就会出现两种事故：客户端已经收到成功，账上没有收据；或者明显会被限流的请求先锁住余额。整个进程的流数量上限留在冻结之后，是个例外。那种暂时不可用会留下随后释放的执行记录，要主动讲出来。

2. 成员关系已经变了，内存里的 Key 还在，怎么保证不会扣错人？

答：扣费身份来自核对数据库之后得到的组织和成员，不来自调用方参数，也不来自可能过期的快照。核对钉住的是创建 Key 时的那一次成员关系。对不上就拒绝，旧 Key 不会记到后来新的成员关系上。

3. Redis 停了，钱会不会错？

答：限流会受影响，收据的投递会延迟。已经写入数据库的收据还在，恢复后可以再投递。结算按执行编号幂等，重放不会扣两次。Redis 里的计数不是余额。

4. 上游已经生成了内容，但收据没写成功，为什么不把冻结退掉？

答：如果已经尝试写收据但结果不确定，就先持有冻结，不写放弃标记。数据库恢复后核对已有收据；没有收据、超过恢复窗口且实例仍存活或心跳未知的执行进入人工核对。若只是中途取消或断流，尚未遇到终态用量异常或收据写入失败，则按放弃标记恢复，哪怕交付过部分内容也可能全额退回。这是平台承担未知成本的政策，不代表上游没有收费。

5. 如果要说这个项目还不能当成生产结论，边界在哪？

答：开发环境里，身份、额度、计费、权限和恢复演练有验收记录。还没有验证的是生产双向证书、真实付费上游、长时间运行，以及生产数据上的备份恢复。成员级模型限制留了叠加位置，没有对应的存储，不能算已实现。本地库可以整库重建，不等于生产账务可以删。

## 12. 练习顺序

1. 先讲系统是做什么的、四块各自写什么、一次调用的顺序。
2. 再讲为什么先用哈希认 Key，然后还要再查一次库。
3. 然后讲冻结上限、收据先于结束标记、同一笔不扣两次。
4. 最后讲主备只在第一个字节之前、多进程时哪些上限会被放大，以及哪些能力还不能说已经完成。

每题停在设计取舍。被追问到命令、端口和页面路径时，再回到[开发说明](DEVELOPMENT.md)，不要把它混进设计答案。
